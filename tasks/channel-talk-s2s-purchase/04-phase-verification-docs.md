# Phase 4: Verification And Docs

## 공통 진행 지시사항

- 이 phase가 끝나면 반드시 커밋한다.
- 커밋 전에 자동 테스트와 필요한 수동 확인을 수행하고, 확인한 명령이나 화면을 기록한다.
- phase 종료 시 회귀 위험과 개선사항을 리뷰한다.
- 완료한 내용, 검증 결과, 남은 위험, 개선사항은 `completion-log.md`에 업데이트한다.
- 구현 중 배운 내용 때문에 남은 작업 순서나 범위가 달라지면 이후 phase 문서도 함께 업데이트한다.
- 계획과 실제 구현이 다르면 실제 구현을 기준으로 문서를 고친다.
- 외부 API 실패를 숨기는 fallback을 추가하지 않는다. 실패 원인과 재시도 상태를 추적할 수 있게 남긴다.
- DB trigger는 사용하지 않는다. 구매 후속 작업은 모델, 서비스, job처럼 코드에서 보이는 경로로 처리한다.
- 기존 작업자의 변경 사항을 되돌리지 않는다. unrelated dirty worktree는 그대로 두고 필요한 파일만 좁게 수정한다.

## 목표

S2S purchase 연동을 면접과 실무 설명에 사용할 수 있도록 검증하고 문서화한다.

## 구현 범위

- 전체 test suite 실행
- 주요 구매 흐름 수동 확인
- 채널톡 API 키가 있는 경우 실제 한 건 전송 확인
- README의 실행 방법과 환경변수 설명 업데이트
- `/debug/channel` 또는 별도 개발자 화면에 S2S delivery 상태를 보여줄지 결정
- phase 문서와 실제 구현 차이 정리
- `completion-log.md` 최종 업데이트

## 데모 시나리오

1. 로그인한 고객이 상품을 장바구니에 담는다.
2. 장바구니에서 구매 완료를 실행한다.
3. 내부 DB에 `purchase` 이벤트가 생성된다.
4. delivery가 `pending`으로 생긴다.
5. job이 delivery를 `processing`으로 바꾸고 `memberId`로 채널톡 User를 조회한다.
6. 채널톡 내부 `userId`가 mapping에 저장된다.
7. 채널톡에 `Purchase` 이벤트가 전송된다.
8. delivery 상태가 `sent`로 바뀐다.
9. 실패 케이스에서는 `failed`, `last_error`, attempts로 원인을 확인한다.

## 사용자 관점 설명

이 phase의 목적은 “구매 이벤트가 채널톡에 갔다”를 개발자만 아는 상태로 두지 않는 것이다. 면접관이나 고객사 개발팀이 봤을 때 어떤 고객의 어떤 주문이 어떤 채널톡 이벤트로 연결됐는지 설명할 수 있어야 한다.

## 검증 방법

- `bin/rails test`
- `bin/rails db:migrate db:seed`
- 로그인, 장바구니 담기, 구매 완료 흐름 수동 확인
- delivery 성공/실패 상태 확인
- 중복 job 실행 시 같은 delivery가 두 번 전송되지 않는지 확인
- README의 환경변수만 보고 새 개발자가 흐름을 이해할 수 있는지 점검
